## 2. Категория A: Неуместный хардкод и перевод на датапаки (Главный приоритет)

### Проблема A.1: Хардкод базовых биржевых товаров в Java-коде
* **Локация:** [`MarketManager.java`](src/main/java/com/exchange/mod/core/MarketManager.java) (строки 61–70)
* **Текущая реализация:**
  ```java
  private void registerDefaults() throws SQLException {
      addAndSave(new MarketResource("minecraft:iron_ingot", "Iron Ingot", 12.0, 10000.0, 10000.0, 0.8, 15000.0, 15.0, 0.02, 0.10));
      addAndSave(new MarketResource("minecraft:gold_ingot", "Gold Ingot", 40.0, 5000.0, 5000.0, 0.85, 8000.0, 20.0, 0.02, 0.20));
      addAndSave(new MarketResource("minecraft:diamond", "Diamond", 350.0, 2000.0, 2000.0, 0.9, 3500.0, 40.0, 0.02, 1.0));
      ...
  }
  ```
* **Почему это плохо:** 
  - Невозможно изменить базовые цены, эластичность, целевые резервы или комиссии дефолтных предметов без перекомпиляции мода.
  - Кастомные предметы загружаются из отдельного файла `config/exchange_custom_items.json` через кастомный парсер, который не умеет перезагружаться через команду `/reload` и не интегрируется со стандартными модпаками.
* **Решение (Datapack):**
  - Реализовать систему загрузки товаров через **NeoForge Data Maps / Codec Datapack Reload Listener** (`data/<namespace>/exchange/commodities/*.json`).
  - Все дефолтные ресурсы вынести в стандартные JSON-файлы внутри мода:
    `data/exchange/commodities/iron_ingot.json`, `diamond.json` и т.д.
  - Любой создатель сборки сможет переопределить любой параметр товара или добавить свой через обычный датапак.

### Проблема A.2: Хардкод экономических событий и кризисов
* **Локация:** [`MarketEventManager.java`](src/main/java/com/exchange/mod/core/events/MarketEventManager.java) (строки 24–75)
* **Текущая реализация:**
  - В методе `registerTemplates()` захардкожены 6 событий: `"GOLD_RUSH"`, `"DIAMOND_COLLAPSE"`, `"CONSTRUCTION_BOOM"`, `"NETHERITE_DISCOVERY"`, `"REDSTONE_AUTOMATION"`, `"EMERALD_EMBARGO"`.
  - Заголовки, описания, затронутый ресурс (`resourceId`), процент изменения цены (`-0.25`, `+0.35`) и длительность вшиты в Java на русском языке.
* **Почему это плохо:**
  - Игроки и администраторы серверов не могут добавить кризисы на ресурсы из модов (например, на медь Create, резину или нефть).
  - Нет интернационализации: английские клиенты видят русские тексты новостей.
* **Решение (Datapack):**
  - Вынести шаблоны экономических событий в датапаки: `data/<namespace>/exchange/events/*.json`.
  - Структура JSON: `id`, `translation_key_title`, `translation_key_desc`, `affected_resource_tag` или `item_id`, `price_multiplier`, `duration_days`, `weight`.

## 3. Категория B: Несоответствие валюты (USDT vs CBX)

По решению пользователя в моде должна быть **строго зафиксирована валюта CBX (ChainBX)**, а все упоминания USDT должны быть полностью ликвидированы.

### Обнаруженные места присутствия USDT:
1. **Языковые файлы (`ru_ru.json`, `en_us.json`):**
   - Строка 243: `"gui.exchange.terminal.err_no_usdt": "Не хватает USDT на балансе!"`
   - Строка 459: `"...на USDT по рыночной цене."`
   - Строка 468: `"Инвестиции в сырье напрямую в USDT..."`
   - Строка 676: `"message.exchange.shop.revenue_credited": "...+%s USDT..."`
2. **Java-код и переменные:**
   - `PlayerAccount.java`: поле `balanceUsdt`, методы `getBalanceUsdt()`, `deposit()`, `withdraw()`.
   - `OMSPosition.java`: поле `investedUSDT`, методы `getInvestedUSDT()`.
   - `LimitOrder.java`: поле `reservedUsdt`.
   - `DeliveryContract.java`: поле `collateralUsdt`.
   - `P2PBuyRequestRecord.java`: поле `escrowUsdt`.
   - `MarketManager.java`: сообщения типа `"Insufficient USDT balance"`, `"OMS Position closed: +X USDT"`.
   - `ExchangePeripheral.java`: метод `getAccount` возвращает поле `"balanceUSDT"`.
3. **База данных SQLite (`DatabaseManager.java`):**
   - Столбцы: `balance_usdt`, `invested_usdt`, `reserved_usdt`, `collateral_usdt`, `fee_usdt`, `escrow_usdt`.
   - *План миграции:* В SQLite сохранить совместимость через автоматическую миграцию названий столбцов или алиасы.

## 5. Категория D: Архитектура, потокобезопасность и производительность

### Проблема D.1: Монолит `PacketHandler.java` (1890 строк)
* **Описание:** Класс `PacketHandler` нарушает принцип единственной ответственности (SRP). Он содержит в себе сетевую маршрутизацию, экономическую логику, манипуляцию инвентарями и SQL-запросы вперемешку.
* **Решение:** Разбить на специализированные обработчики:
  - `ServerOrderHandler` (маркетные и лимитные ордера)
  - `ServerShopHandler` (вендинг, покупки и улучшения)
  - `ServerEscrowHandler` (P2P RFQ и биржа труда)
  - `ServerWalletHandler` (P2P переводы)

### Проблема D.2: Синхронный SQL на главном тике сервера (Main Thread I/O)
* **Описание:** В `PacketHandler` операции с SQLite (`dao.saveAccount`, `dao.upsertMarket`, `dao.recordTransaction`) вызываются синхронно внутри `context.enqueueWork(() -> ...)`.
* **Риск:** При нагруженном диске время выполнения тика превышает 50 мс, вызывая микрофризы (лаги TPS) на сервере.
* **Решение:** Выполнять тяжелые запросы чтения асинхронно через `CompletableFuture`, а на главном тике производить только забор/выдачу предметов из инвентаря игрока.

### Проблема D.3: Подсчет игрового дня через счетчик тиков
* **Локация:** [`ExchangeMod.java`](src/main/java/com/exchange/mod/ExchangeMod.java) (строки 330–333)
* **Описание:** 
  ```java
  dayTickCounter++;
  if (dayTickCounter >= 24000) { ... }
  ```
* **Риск:** Если игроки спят в кроватях или используется `/time set day`, экономический день наступает не с рассветом, а строго через 20 минут реального времени.
* **Решение:** Отслеживать реальное время мира через `level.getDayTime() / 24000L`.

## 6. Категория E: Баланс экономики, эксплойты и безопасность

1. **Проверка отрицательных цен и утилизационного сбора:**
   - В `MarketManager.java` корректно проверяется баланс игрока на списание экологического сбора при переполнении складов.
   - *Рекомендация:* Убедиться, что при сбросе через воронки и автоматизацию Create в док сбыта (`TradeDockBlock`) товары не «улетают» бесплатно, если баланс владельца ушел в ноль.
2. **P2P Escrow Race Condition (Состояние гонки):**
   - При исполнении заказа на скупку или отмене ордера эскроу проверка статуса заказа и возврат средств должны производиться в единой атомарной транзакции SQLite (`BEGIN IMMEDIATE`), чтобы исключить дупликацию средств при быстром двойном клике.
3. **Бесконтактный кошелек (Cold Wallet):**
   - Проверка дистанции (30 блоков) сейчас захардкожена. Целесообразно вынести радиус действия кошелька в конфиг.
